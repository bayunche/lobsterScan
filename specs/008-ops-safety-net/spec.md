# Feature Specification: P8 — 运营兜底(operational safety net)

**Feature Branch**: `008-ops-safety-net`

**Created**: 2026-06-02

**Status**: Draft

**Input**: User description: "P8 — 运营兜底。三个互相独立、默认关、零回归的子能力:① 预算硬上限(token 累计触顶 → 软着陆收尾出局部产物 + 触顶后不再启动新工作);② rolling summary(群聊上下文超阈值时把更早发言折叠成一行摘要,保持上下文有界);③ yes-man 防御(给审校者注入对立质疑指令,防止橡皮图章式附和)。验收=测试级绿 + 1 次真实端到端。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 预算硬上限,触顶软着陆(Priority: P1)

运营方为一次报告生成设定一个总开销上限。当本次任务累计消耗达到上限时,系统**不再启动任何新的工作环节**,而是用已经完成的成果体面收尾:能凑齐完整报告就正常交付,凑不齐则交付一份「局部完成」的报告,并在群聊里以业务化措辞告知「为控制开销先收尾」。绝不丢弃任何已完成的成果,也绝不在触顶后继续无限消耗。

**Why this priority**: 这是上线安全网的核心——没有硬上限,失控的循环或异常可能无限消耗预算。是三者中唯一直接防止「钱烧光」的兜底,最高优先级。

**Independent Test**: 设一个很低的上限,跑一个任务,验证:消耗触顶后没有新环节启动、最终状态为「局部完成」(若产物不齐)、已完成环节的成果都在、群聊出现一条不含任何技术编号的「控制开销收尾」发声。

**Acceptance Scenarios**:

1. **Given** 上限设为 0(关闭), **When** 跑完整任务, **Then** 行为与未引入本能力时完全一致(无任何收尾干预、无新发声)。
2. **Given** 上限设为一个较低正值, **When** 累计消耗达到或超过上限, **Then** 系统停止启动新工作环节,并触发一次收尾决策。
3. **Given** 触顶时 4 项核心产物已齐, **When** 收尾决策执行, **Then** 任务以「完成」状态交付。
4. **Given** 触顶时核心产物不齐, **When** 收尾决策执行, **Then** 任务以「局部完成」状态交付,已完成产物全部保留。
5. **Given** 触顶, **When** 系统在群聊发声告知收尾, **Then** 该发声为业务化中文,不含 token 数、任务编号、同事内部代号等技术信息。
6. **Given** 已触顶收尾, **When** 后续有环节本应被激活, **Then** 不再启动该环节(去重,只软着陆一次)。

---

### User Story 2 - rolling summary,上下文有界(Priority: P2)

在较长的任务里,群聊发言会不断累积。为防止注入给同事的「群聊上下文」无限膨胀(进而推高开销、稀释重点),当上下文发言条数超过阈值时,系统把较早的发言折叠成一行简短摘要,只逐条保留最近的若干条,使每位同事看到的上下文长度始终有界。

**Why this priority**: 防止长任务下上下文膨胀,与预算硬上限互补(反向减少消耗),但本身不直接防失控,故次于 P1。

**Independent Test**: 构造超过阈值条数的群聊发言,渲染上下文,验证:最近若干条逐条保留、更早的被折叠成单独一行摘要、总条数受控;条数未超阈值时上下文原样不折叠;上下文数据源缺失时安全降级为空。

**Acceptance Scenarios**:

1. **Given** 能力关闭(默认), **When** 渲染群聊上下文, **Then** 行为与未引入本能力时一致(不折叠)。
2. **Given** 能力开启且发言条数未超阈值, **When** 渲染上下文, **Then** 全部发言逐条保留,不折叠。
3. **Given** 能力开启且发言条数超阈值, **When** 渲染上下文, **Then** 最近若干条逐条保留、更早的合并为一行摘要,且摘要不含技术编号。
4. **Given** 上下文数据源不可用, **When** 渲染上下文, **Then** 安全返回空,不报错、不阻塞任务。

---

### User Story 3 - yes-man 防御,审校不橡皮图章(Priority: P3)

为防止审校环节流于形式地附和(「看上去 OK」),运营方可开启「对立质疑」模式:开启后,审校者被明确要求主动挑刺、假设作者可能夸大、对不达标的内容如实指出,而非默认放行。

**Why this priority**: 提升产出质量的安全网,但不影响成本/稳定性,且为纯措辞调整,风险与紧迫性最低,故为 P3。

**Independent Test**: 分别在开启/关闭两种状态下检查审校者收到的指令文本,验证开启时含「对立质疑」类要求、关闭时不含;关闭为默认。

**Acceptance Scenarios**:

1. **Given** 能力关闭(默认), **When** 审校者点评产物, **Then** 指令与未引入本能力时一致。
2. **Given** 能力开启, **When** 审校者点评产物, **Then** 其指令包含主动找瑕疵、不橡皮图章的对立质疑要求。

---

### Edge Cases

- 三个能力**任意组合开启**时互不干扰(彼此正交),且都与已有的 prompt 模式 / 并发开关正交。
- 预算上限恰好在某环节运行**过程中**被跨越:正在运行的环节允许跑完(其成果保留),只阻止**新**环节启动。
- rolling summary 阈值设得极小(如 1):仍须正确保留最近一条、折叠其余,不报错。
- 任一能力内部异常:降级回该能力关闭时的行为,绝不阻塞报告产出。
- 预算累计计数遇到缺失/异常的消耗数据:按 0 计,不抛错。

## Requirements *(mandatory)*

### Functional Requirements

**通用(贯穿三能力)**

- **FR-001**: 三个能力 MUST 各自由独立开关控制,默认值 MUST 为「关闭」。
- **FR-002**: 三个能力在全部关闭时,系统行为 MUST 与引入本特性之前**逐字段一致**(零回归)。
- **FR-003**: 三个能力之间、以及与已有的上下文模式开关、并发开关之间 MUST 互相正交(任意组合可独立生效)。
- **FR-004**: 任一能力内部发生异常时,系统 MUST 降级回该能力关闭时的行为,不得阻塞或失败整个报告产出。
- **FR-005**: 任何面向用户的发声 MUST 为业务化中文,不得泄漏技术编号(任务编号、同事内部代号、token 数等)。

**预算硬上限(US1)**

- **FR-006**: 系统 MUST 在任务级别累计本次任务消耗的开销量(以 token 计)。
- **FR-007**: 上限为 0 时 MUST 视为「不限」,即关闭本能力。
- **FR-008**: 当累计消耗达到或超过正的上限时,系统 MUST 停止启动任何新的工作环节。
- **FR-009**: 触顶后系统 MUST 执行一次收尾决策:核心产物齐 → 「完成」;不齐 → 「局部完成」。
- **FR-010**: 触顶收尾 MUST 保留所有已完成环节的成果,不得丢弃。
- **FR-011**: 触顶收尾 MUST 在群聊发出一条告知性发声(说明为控制开销而收尾)。
- **FR-012**: 触顶软着陆 MUST 只触发一次(去重),不得重复收尾。

**rolling summary(US2)**

- **FR-013**: 当群聊上下文发言条数超过阈值时,系统 MUST 只逐条保留最近若干条,并把更早的折叠为一行摘要。
- **FR-014**: 发言条数未超阈值时,系统 MUST 原样保留全部发言,不折叠。
- **FR-015**: 折叠摘要的生成 MUST 为确定性规则(不依赖额外的智能判断),且摘要文本不得泄漏技术编号。
- **FR-016**: 上下文数据源不可用时,系统 MUST 安全返回空上下文,不报错。

**yes-man 防御(US3)**

- **FR-017**: 开启时,系统 MUST 给审校环节注入「对立质疑」指令(主动找瑕疵、假设可能夸大、不橡皮图章式放行)。
- **FR-018**: 关闭时,审校环节收到的指令 MUST 与引入本能力之前一致。

### Key Entities *(include if feature involves data)*

- **预算计数器**:任务级别的累计消耗量(token)与触顶标志;关系:归属单次任务,任务间互不影响。
- **上下文窗口**:群聊最近发言的有界视图,含「保留尾部条数」与「折叠阈值」两个参数。
- **审校指令**:审校者收到的点评指令,含一个可选的「对立质疑」前置段。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 三个能力全部关闭时,既有回归测试 100% 通过,产出与引入前逐字段一致(零回归)。
- **SC-002**: 设较低预算上限跑一次真实任务,累计消耗触顶后**新启动环节数为 0**,且最终交付一份保留全部已完成成果的报告(完整则「完成」,否则「局部完成」)。
- **SC-003**: 预算触顶时群聊发声 100% 不含技术编号(token 数 / 任务编号 / 内部代号)。
- **SC-004**: rolling summary 开启且发言超阈值时,注入给同事的上下文条数 ≤(尾部保留条数 + 1 行摘要),且摘要不泄漏技术编号。
- **SC-005**: yes-man 开启与关闭两种状态下,审校指令文本可被区分(开启含对立质疑要求、关闭不含),且开启不影响任务能否正常收尾。
- **SC-006**: 任一能力内部注入异常时,任务仍能产出报告(降级生效),不出现整体失败。

## Assumptions

- 单次消耗量(token)数据由现有的「单轮执行结果」提供;预算只做单一累计的硬上限,不区分服务商/通道(细粒度计费为非目标)。
- 预算为单次任务范围(per-task),不做跨任务的全局预算池(非目标)。
- rolling summary 默认采用确定性规则折叠;真正用智能模型生成摘要为非目标(可后续扩展)。
- 三个能力沿用既有的「开关默认关 = 零回归」范式;开关粒度为运行期可配置。
- 「核心产物齐全」的判定沿用既有的收尾校验口径(4 项核心产物)。
- 验收基线为「测试级全绿 + 1 次真实端到端」,与本路线图既往阶段一致。
