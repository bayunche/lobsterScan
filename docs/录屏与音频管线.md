> 关键文件：`apps/web-backend/app/render/html_builder.py` / `broadcast_recorder.py` / `slideshow_video.py` / `tts_fallback.py`

## 一、两张 HTML 的分工

pipeline 的 `html_design` step 同时渲两张 HTML 到 `data/outputs/<task>/web-presentation/`：

| 文件 | 给谁看 | 资源引用 | self-contained | 录屏用 |
| --- | --- | --- | --- | --- |
| `index.html`（presenter） | 真人讲解者本地打开预览 | 视频 = 相对路径 `../video/intro.mp4` | 否，须保留同级 `../audio/` `../video/` 才能跑 | 否 |
| `broadcast.html` | playwright headless chromium | 音频 = `file://` 绝对路径 | 否，**仅同机有效**（playwright 录完即弃） | **是** |

> ⚠️ 别再 base64 inline。早期 broadcast.html 把 mp3 base64 嵌进 HTML 自封装，4MB/段硬上限被 3~5 分钟汇报的长 narration 经常打爆，导致那段录出来是哑剧。现在改 `file://`。

## 二、音频改 file:// 的来龙去脉

实现入口 `html_builder.py:20`：

```python
_AUDIO_MAX_BYTES = 1000 * 1024 * 1024  # 1000MB/段兜底

def _audio_file_url(path: Path) -> str:
    if not path.exists() or path.stat().st_size == 0:
        return ""
    if path.stat().st_size > _AUDIO_MAX_BYTES:
        return ""
    return path.resolve().as_uri()   # → file:///mnt/c/code/.../audio/01.mp3
```

为什么 file:// 能跑通 chromium autoplay + 同源访问：

1. **同源**：broadcast.html 本身就被 playwright 用 `page.goto(broadcast_path.as_uri())` 打开（`broadcast_recorder.py:76`），主页是 `file://`，子资源 `file://` → 同源，无需 `--allow-file-access-from-files`。
2. **autoplay**：chromium launch 加了 `--autoplay-policy=no-user-gesture-required`（`broadcast_recorder.py:65`），audio 不需要点击就播。
3. **1000MB 兜底**：实际语音 mp3 单段不可能这么大（128kbps × 1000MB ≈ 17 小时），这个数字纯是防 path 指错巨型文件，真正起作用的判断是「文件存在 + size > 0」。
4. **audit 字段**：`broadcast_audit.json` 写出 `_audio_total_kb`（不是 inline 字节，是引用到的 mp3 总大小）。前端 / 管台没人读这字段，只当落盘审计。

> ⚠️ 取舍：broadcast.html 不再 self-contained，单独拷走会丢音。但 broadcast.html **设计目的就是同机录屏给 playwright 用**，用户对外分享走 presenter.html（里面有 video chip 链到 recording.mp4）。这是预期行为。

## 三、playwright 录屏流程

入口 `broadcast_recorder.py:record_broadcast()`：

```
broadcast.html  +  audio_segments[]
        │
        ▼
1. playwright chromium 1920×1080 headless
       │  --autoplay-policy=no-user-gesture-required
       │  record_video_dir=<tmp>
       ▼
2. page.goto(broadcast.html as file://)
3. wait_for_function("window.__broadcastReady === true", 20s)
4. totalSec = await page.evaluate("window.__broadcastTotalSec")
5. asyncio.sleep(totalSec + 2.0)
6. context.close()  →  flush webm
        │
        ▼
7. ffmpeg webm → mp4(libx264 + aac，180s 超时)
        │
        ▼
8. _probe_has_audio(mp4)：检 ffmpeg stderr 是否含 "Audio:"
   ├─ 有 → 直接返回
   └─ 无 → 走音轨 mux（第 9 步）
        │
        ▼
9. _concat_audio_segments：把 audio_segments 拼成 _audio_concat.aac
       │  失败的段填 anullsrc 静默占位（保 duration 对齐）
       ▼
10. _mux_audio_into_video：ffmpeg -c:v copy -c:a aac -map 0:v:0 -map 1:a:0 -shortest
        │
        ▼
recording.mp4（带音轨，h264 + aac）
```

关键约定：

- **broadcast.html 必须暴露 `window.__broadcastReady` 和 `window.__broadcastTotalSec`** — 没有就走 60s 兜底（`broadcast_recorder.py:93`）。改 broadcast.html 模板时要保留这两个全局。
- **playwright 自己只录视觉帧不录系统音频** — 即便 chromium autoplay 了 audio 元素也录不进去。所以 audio 必须走 mux 路径。`has_audio=True` 实际是 mux 后的状态，不是 webm 本身。
- **threadpool runner**（`record_broadcast` L264-281）：在 FastAPI 已有 running loop 的场景下，asyncio.run() 会炸；嵌一个 ThreadPoolExecutor 起新 loop 跑 playwright，规避事件循环冲突。

## 四、slideshow fallback（数字人 fail 兜底）

`pipeline.py:_maybe_build_slideshow_fallback` 在数字人 provider（HeyGen / Kling / Hailuo）产物校验失败时启动：

```
agent video step done
       │
       ▼
_verify_agent_recording_claims：
  intro_video / outro_video / segments[*].video 是否真存在且 > 50KB
       │
       ├─ 全过 → 写 video_production.json，结束
       └─ 任一段 fail
                │
                ▼
        _ensure_audio_segments：
          中间页 narration → mmx CLI / edge-tts 合成 mp3
          intro / outro 文本 → 同上
                │
                ▼
        slideshow_video.py：
          slides PNG（Pillow 拼版）+ imageio-ffmpeg 合成 slideshow.mp4
                │
                ▼
        full_segs = [intro audio] + middle audio_segments + [outro audio]
        record_broadcast(broadcast.html, recording.mp4, full_segs)
                │
                ▼
        recording.mp4 写到 video_production.json 的新字段 `recording`
        （不再覆盖 intro_video，避免和 agent 已交付的产物混淆）
```

> ⚠️ **full_segs 顺序**是历史踩坑点：早期 mux 只拿 `audio_segments`（仅中间页），结果带数字人的 intro/outro 段静音。Fix 是把 intro_audio + middle + outro_audio 全拼起来，跟 broadcast.html 的页面顺序对齐。

`_ensure_audio_segments`（`pipeline.py`）确保 mmx CLI（优先）或 edge-tts（fallback）能给每段产出 mp3，即使 video provider 出问题。TTS 走 `tts_fallback.py`，参考 [[mmx-cli-first]]。

## 五、时序：何时重渲 broadcast.html

```
html_design step 完成 → 渲 broadcast.html v1（audio 段路径占位）
       │
video_production step 完成 → audio_segments 落地 + 数字人 mp4 落地
       │
       ▼
重渲 broadcast.html v2（pipeline.py:2216-2223）
  · audio_segments[*].src 替换为 file://...
  · avatar 段 media 替换为真实 video 路径
  · 这次才是 playwright 实际录屏用的
       │
       ▼
record_broadcast → recording.mp4
```

不要在 html_design 后立刻录屏 — audio 还没合成、avatar 还没生成，录出来必然有缺。重渲是 pipeline 强约束的一步。

## 六、调试 checklist

录屏出问题先按这个清单走：

1. **broadcast.html 自己打不打得开**：浏览器手动打开 `data/outputs/<task>/web-presentation/broadcast.html`，看页面是否能跑完、音频是否有声。
2. **`window.__broadcastReady` 是不是 true**：DevTools console 输入 `window.__broadcastReady`、`window.__broadcastTotalSec`，前者必须 true、后者必须 > 0。
3. **audio_segments[*].src 是不是 file://**：DevTools console 输入 `window.__DATA__.audio_segments[0]`，src 应该是 `file:///...` 不是 `data:audio/...`。
4. **mp3 文件真在那**：`ls -la data/outputs/<task>/audio/`，对照 audit 文件 `broadcast_audit.json` 里 `audio_segments[*].path`。
5. **playwright chromium 起不起来**：跑 `python -m playwright install chromium` 装 binary，看 `~/.cache/ms-playwright/` 有没有。
6. **mp4 有没有音轨**：`ffprobe -i recording.mp4 2>&1 | grep Audio`，没行就是 mux 没成。看 pipeline 日志 `audio concat failed` / `mux failed`。
7. **总时长对不齐**：broadcast.html JS 算 totalSec 时按 audio.duration 加和；如果 audio 缺失，page 跳过那段，但 broadcast_recorder 还在按 totalSec 录 — 没法补，只能保证 audio_segments 全 ok。
